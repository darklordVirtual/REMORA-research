## The §99 cases (`tooling/sec99_repro.py`, `cases.json`)

The script holds what the 2026-11-02 review held, the agent token, plus the lease key. It asks for a read (`read_sensor PT-101`) rather than the review's valve move. The property under test is who may dispatch under a lease.

| Case | Expectation | Observed |
|---|---|---|
| N1, six cases: self-signed lease, linked and unlinked, on the authority with the agent, approver and supervisor tokens | 404, nothing dispatched | 404 each |
| N2: agent (operator) token on the executor | 403 | 403 |
| N3: `dispatch_hop` token, valid signature, empty `proposal_id` and `grant_jti` | `executed=false`, `lease_unlinked` | as expected |
| P1: `dispatch_hop` token, valid signature, non-empty linkage | executed with `lease_dispatch_admitted` before and `lease_dispatch_result` after on the chain, or a named refusal | `executed=true`; chain sequence 35 (`admitted`) then 36 (`result`, `executed=true`) |
| N4: the call under the P1 lease changed after signing | refused | `executed=false`, `tool_args_hash_mismatch`; chain 37, 38 |
| N5: the P1 lease presented again | refused | `executed=false`, `nonce_already_consumed`; chain 39, 40 |

11 of 11 cases behaved as the repair specifies. The authority's `/v1/execution/audit/verify` went from 35 to 41 records across the run and reported `INTACT`, `signature_status CHECKED`; the six new records are the executor's, read back from `tenant_chain_entry` in `chain-readback.jsonl` with their hashes. In this topology the two processes share one tenant chain, so the §99 limitation about separate stores did not arise; it still applies to a deployment with separate stores.

P1 is also the limit the §99 text names: `prop-fabricated-1` and `grant-fabricated-1` exist nowhere, and the executor ran the read. "Linked" is a non-empty check, not authenticated linkage. What keeps an agent from doing this is custody of the lease key (the strict profiles' Ed25519 split), not this check.

## The OT battery and fault injection on the same build

- `battery/`: `deploy/ot-pilot/run_ot_battery.py`, 16 of 16 cases as specified on the fresh stack before the §99 cases ran. Six real side effects executed, all under signed work orders and approvals. The five monitoring reads went to review (0/5 completed without review). The battery reports that; it is the WS1 utility question, not a §99 question.
- `fault-injection/first-run-not-fresh/`: `deploy/ot-pilot/run_fault_injection.py` on the stack after the battery and the §99 cases: 9 of 10. "Cumulative limits across a restart" failed at its setup call with `limit_exceeded`, because the battery's limit case had already spent PIC-101's hourly movement cap on the same ledger. The runner documents that it expects a fresh stack. Kept as a negative record, not smoothed over.
- `fault-injection/fresh-stack/`: the same runner after `down -v` and `up`: 10 of 10. The cases include spent-grant replay across a restart, four concurrent executions of one approval, Postgres stopped during a governed write, and approver revocation after approval.
- Redaction: both fault-injection `manifest.json` files as written by the runner contained the approver bearer token, although the runner's own text says it records no environment values. The token is replaced here by `<redacted:OT_TOKEN_APPROVER>`, and the leak is a follow-up on the runner. The pilot's credentials were rotated out of use when the stack was torn down.

## How to reproduce

```
python deploy/ot-pilot/init_tokens.py
docker compose -f deploy/ot-pilot/docker-compose.yml up --build -d
# fill the placeholders in tooling/docker-compose.executor.yml from deploy/ot-pilot/.env, one new dispatch_hop token,
# and OT_LIMITS_TRUSTED_KEYS from the base compose file
docker compose -f deploy/ot-pilot/docker-compose.yml -f tooling/docker-compose.executor.yml up -d executor
set -a; . deploy/ot-pilot/.env; OT_TOKEN_HOP=<the hop token>; set +a
python tooling/sec99_repro.py <output dir>
python deploy/ot-pilot/run_ot_battery.py
docker compose -f deploy/ot-pilot/docker-compose.yml down -v && docker compose -f deploy/ot-pilot/docker-compose.yml up -d
python deploy/ot-pilot/run_fault_injection.py --evidence-root <dir>
```

These are the author's runs on one host. They are not an independent reproduction (M4.4) and not OT deployment validation.
