\begin{abstract}
REMORA is a governed execution-assurance layer for tool-using AI agents.
An agent's intention is not an effect. A deterministic policy gate routes
each proposed call to \textsc{accept}, \textsc{verify}, \textsc{abstain} or
\textsc{escalate} before dispatch. A signed ToolSpec states what an approval
covers, and an exact-call \texttt{ExecutionLease} binds that approval to one
tool, argument set, target and policy bundle. A single-use grant is consumed
at an enforcement point that re-evaluates policy. The lifecycle records
\emph{authorized}, \emph{dispatched}, \emph{executed} and \emph{verified
effect} as separate claims. Model consensus cannot override a hard block.

Its mechanisms are individually known: capabilities with caveats, reference
monitors, policy engines and tamper-evident logs. The contribution is a
systems artifact that integrates them, together with an evaluation method of
sealed, pre-registered tracks whose misses and negative results are published.

On a leakage-controlled 700-task tool-call simulator benchmark (effective
$N=70$) the full gate produced zero unsafe acceptances, 0 of 56 harmful
templates (Wilson 95\% upper bound 6.4\% over those templates). Keyword baselines reached 1.4\%, a difference that is not
significant, and a component ablation attributes the result to no single
component (CLAIM-001, CLAIM-020). On 208 AgentHarm scenarios
\cite{andriushchenko2024agentharm} an imported intent-gating run made no
false authorization but also blocked every benign counterpart, so it shows no
discrimination (CLAIM-002). With every state verdict \textsc{unknown},
bounded verification let 60/60 valid-identifier reads proceed autonomously,
against 0/60 without validators, a baseline that is zero by construction
(CLAIM-014).

Sealed BFCL v4 tracks measure routing within one tool catalogue. REMORA
routes annotated calls; it does not generate them, and each wrong call is
another task's correct call substituted into the task, almost always a
tool the task never offered. In a sealed C-ext3
track, declared tool contracts and task intents re-derived from the task text
accepted 0/500 wrong calls (Wilson 95\% upper bound 0.76\% by row,
3.5\% clustered by tool). Four of the seven pre-registered targets were
missed. One of them is a safety target: 2 of 199 constructed wrong-tool
calls were accepted (1.005\%, against a bar of at most 1\%). Legitimate
read autonomy was 26.6\% against a 75\% target, and both argument-routing
targets were missed, so the pre-registered joint hypothesis was not
supported (CLAIM-019). A final sealed
track, C-ext4, spent the remaining BFCL v4 reserve (1{,}562 episodes) on a
revised bundle. It accepted 29.9\% of correct calls against 6.9\% for the
C-ext3 bundle and accepted no wrong call, as did a refuse-all control. The
gain sits on tools seen during development, so transfer to new tool families
is untested (CLAIM-021). The earlier sealed track's 10.9\% wrong-call rate is
kept as the baseline (CLAIM-018, superseded by CLAIM-019).

Each result cites its claim-register entry, and machine-readable capability
and boundary declarations state what the system establishes and what it does
not. A post-hoc attack evaluation of the execution chain, on the author's
own catalogue, is in \S\ref{sec:negative}. REMORA ran none of 43 chain
attacks and a policy-only gateway ran 33, while the secret reached the sink
in all 11 exfiltrations built from allowed calls, on both. One
frozen interoperability contract has two external fixture-level runs that
meet the repository's independence rule; production enforcement
remains unestablished, and the declared deployment status is
\texttt{SHADOW\_ONLY}: shadow-mode operation is permitted, enforcement is not.
\end{abstract}

\textbf{Keywords:} agentic AI safety, AI control, agent security,
governance overlay, policy-as-code, selective prediction, uncertainty
routing, audit governance, human-in-the-loop.

\section{Introduction}
\label{sec:intro}

An operator asks a fleet assistant for the status of vehicle
\texttt{V-0042}. The assistant proposes
\texttt{get\_vehicle(vehicle\_id="V-0042")}: the right tool and an
identifier drawn from the request. REMORA first routes the read to
\textsc{verify} because the identifier has not been confirmed against
the system of record. A bounded lookup confirms it; the full policy
gate runs again on the fresh observation and can return \textsc{accept}.
The assistant gets a path to a useful answer without treating an
unverified value as authority (\S\ref{sec:casestudy-fleetops}).

The research hypothesis is that agent autonomy becomes more useful
when uncertainty determines \emph{what to check}, while deployment-owned
authority determines \emph{what may run}. These are different jobs.
Deterministic rules bind a call to a declared tool, permitted target and
policy, and a hard block cannot be voted away. Probabilistic disagreement
and evidence signals can help route an ambiguous proposal toward
verification or review; in REMORA they are studied on a separate research
path, not entrusted with execution permission. This separation lets us
measure routing quality without mistaking model confidence for authority.

The clearest test of that hypothesis concerns a call that passes
structural checks but uses the wrong tool for the task. In a sealed
C-ext3 study of 2{,}799 episodes, declared tool contracts and task
intents re-derived from the task text reduced acceptance of substituted
wrong calls to 0/500 (Wilson 95\% upper bound 0.76\% by row, 3.5\%
clustered by tool). The arm comparison recorded 24, then 6, then 0 accepts
as semantic authority was introduced; the paired test was run only after
the fact
(\S\ref{sec:wrongcall-implication}, CLAIM-019). The promising mechanism
is explicit semantic authority, not a more confident model vote. Its
measured property is contract-authorized read, not guaranteed task success
or live deployment performance. Its current price matters: the deterministic intent extractor allowed only
26.6\% of legitimate reads to proceed autonomously in that study, so the
pre-registered joint hypothesis, which also required 75\% read autonomy,
was not supported. The same run accepted 2 of 199 constructed wrong-tool
calls against a safety bar of at most 1\% and missed both argument-routing
targets, four of its seven targets in all
(\S\ref{sec:wrongcall-implication}). A later
sealed track raised correct-call acceptance from 6.9\% to 29.9\% with a
revised bundle and no wrong call accepted, mostly on tools seen in
development; a refuse-all control also accepted no wrong call
(\S\ref{sec:wrongcall-implication}, CLAIM-021).
Bounded verification offers another path to useful autonomy when task
state is unknown (\S\ref{sec:casestudy-fleetops}, CLAIM-014).

REMORA places a decision boundary between a proposed call and its
effect. Deployment-owned tool definitions and policy determine what the
call is allowed to do. The gate may \textsc{accept} it, require a bounded
lookup (\textsc{verify}), decline autonomous action (\textsc{abstain}),
or send it to a person (\textsc{escalate}). A model's confidence cannot
override a hard policy block. \textsc{accept} permits the next
authorization step; it says nothing about whether the action is correct.
Execution still requires authority bound to that exact call, a
single-use grant and another policy check at dispatch.

That distinction continues after the call runs. Authorization,
dispatch, execution and verified effect are recorded separately; a
successful transport response does not establish what changed in the
target system. The decision record also states which parts of the trust
base its evidence covers. This makes it possible to ask a sharper
question than whether an agent \emph{wanted} to act: what authorized the
action, what ran, and what evidence supports the reported outcome?

A second design decision constrains the first: the boundary itself is
declared, not implied. Machine-readable capability and boundary
declarations (\S\ref{sec:boundary-declarations}) state which properties
REMORA establishes at the governed boundary and under which execution
profile. Explicit claim ceilings record what remains unestablished:
alternate credential paths, and the privileged effects an authorized
tool's implementation can reach. REMORA therefore does not claim that
all agent effects are governed; it makes the governed boundary
explicit, and falsifiable.

Related work approaches the same control boundary from different
directions. Progent studies least-privilege tool permissioning
\cite{shi2025progent}. CaMeL separates trusted control from untrusted data
\cite{debenedetti2025camel}, while AIRGuard examines action-time authority
confusion \cite{qin2026airguard}. These studies motivate the problem;
they do not replicate REMORA's results. Here the contribution is an
implemented path from tool authority to exact-call dispatch and distinct
effect evidence, evaluated alongside deterministic and probabilistic
routing experiments. For governed deployments, this would let an agent
suggest useful actions without making its own confidence the source of
permission. The reported numbers are tied to committed
artifacts and their stated scope, not to field validation.

\paragraph{Contributions.} The individual mechanisms are known:
capabilities with caveats \cite{birgisson2014macaroons}, reference
monitors \cite{anderson1972planning}, policy engines and tamper-evident
logs \cite{crosby2009tamper}. The contribution is a systems artifact that integrates
them and an evaluation method around it. This preprint makes five
contributions, each
bound to committed artifacts; Table~\ref{tab:headline} lists the headline
numbers.
\begin{enumerate}[leftmargin=*,itemsep=1pt]
\item an authority-bound execution chain (signed ToolSpec, exact-call
  \texttt{ExecutionLease}, single-use grant, re-policying at dispatch) whose
  lifecycle separates authorization, dispatch, execution and verified effect
  (\S\ref{sec:execution-chain}); it is implemented and tested, and its
  attack evaluation is post hoc and author-run (\S\ref{sec:negative});
\item an argument-resolution ladder in which \textsc{unknown} is a
  first-class verdict and a \textsc{verify} names a bounded lookup followed
  by full re-entry of the router (\S\ref{sec:resolution-ladder},
  \S\ref{sec:casestudy-fleetops});
\item sealed external routing evidence on BFCL v4, a disjoint C-ext3
  track that isolates declared semantic authority, and a C-ext4 track that
  measures a revised bundle against the C-ext3 one, with the utility cost
  and the limits of the gain published as measured (\S\ref{sec:routing-blind},
  \S\ref{sec:wrongcall-implication});
\item machine-readable capability and boundary declarations with explicit
  claim ceilings, a claim register that gates the headline numbers in this paper,
  and a negative-results record that includes an ablation attributing the
  headline safety number to no component
  (\S\ref{sec:boundary-declarations}, \S\ref{sec:ablation});
\item frozen interoperability contracts with external run records, one of
  them with two external fixture-level runs that meet the repository's
  independence rule, together with contract probes and a
  formal model contributed to an external federation transport
  (\S\ref{sec:federation}).
\end{enumerate}
The paper follows that order: related work (\S\ref{sec:related}), the
problem statement and architecture
(\S\ref{sec:problem}--\S\ref{sec:audit}), evaluation and results
(\S\ref{sec:eval}--\S\ref{sec:casestudy-fleetops}), negative results,
validity and reproducibility (\S\ref{sec:negative}--\S\ref{sec:repro}), and
the conclusion (\S\ref{sec:conclusion}). The retired oracle-consensus,
conformal and calibration material is in
Appendices~\ref{app:consensus}--\ref{app:mondrian}.

\section{Background and Related Work}
\label{sec:related}

\subsection{LLM Ensembles and Self-Consistency}
Wang et al.\ (2023) \cite{wang2023self} introduced self-consistency
sampling over chain-of-thought paths. Lakshminarayanan et al.\ (2017)
\cite{lakshminarayanan2017simple} demonstrated that deep ensembles from
distinct random initialisations improve both accuracy and calibration.
REMORA's oracle fan-out is structurally related but uses
\emph{separately configured oracle endpoints} rather than multiple samples
from one model (the 2026-07 clean round and the AgentHarm validation use a
Cloudflare Workers AI cross-family trio (Meta LLaMA, Alibaba Qwen,
Mistral; earlier rounds used a Groq three-LLaMA swarm),
and weights oracles by \emph{inverse pairwise correlation} rather than
treating them as exchangeable. Kuncheva \& Whitaker (2003)
\cite{kuncheva2003measures} formalised diversity measures for classifier
ensembles; REMORA's inverse-correlation weighting can be understood as an
instance of this family applied to instruction-following LLMs.
Wang, Aitchison \& Rudolph (2023) \cite{wang2023lora} show that
parameter-efficient LoRA ensembles improve predictive accuracy and
uncertainty quantification, with ensemble diversity as the key driver;
this motivates, but does not independently validate, REMORA's
heterogeneous oracle aggregation.

\subsection{Multi-Agent Debate}
Du et al.\ (2024) \cite{du2023improving} showed that inter-model
debate can reduce hallucination. REMORA's dissensus metric $D$ is a
one-shot, non-iterative analogue: disagreement is measured once, not
resolved through iterative exchange.

\subsection{LLM-as-Judge and Verifier Models}
Zheng et al.\ (2023) \cite{zheng2023judging} established the
LLM-as-judge paradigm. Cobbe et al.\ (2021) \cite{cobbe2021training}
trained outcome verifiers that rank complete model solutions. REMORA differs by using a \emph{structured policy engine} rather than a
learned verifier, enabling interpretable hard blocks that cannot be
overridden by a confident oracle.

\subsection{Selective Prediction and Abstention}
Chow (1970) \cite{chow1970optimum} established the optimal error-reject
tradeoff for binary classifiers. El-Yaniv \& Wiener (2010)
\cite{elyaniv2010selective} extended this to a distribution-free
selective classification framework; their coverage--accuracy bound, which
assumes a noise-free realizable setting that three LLM oracles do not form,
is the foundational result that Geifman \& El-Yaniv (2017)
\cite{geifman2017selective} apply to deep networks. Kadavath
et al.\ (2022) \cite{kadavath2022language} find promising LLM
self-knowledge on tasks resembling training data, with weaker
calibration and self-evaluation on novel tasks.
REMORA's abstention is grounded in structural oracle disagreement
rather than self-reported confidence.

\subsection{Conformal Prediction}
Conformal prediction originates with Vovk, Gammerman \& Shafer (2005)
\cite{vovk2005algorithmic}; Shafer \& Vovk (2008) \cite{shafer2008tutorial}
and Angelopoulos \& Bates (2021) \cite{angelopoulos2021gentle} established
it as a practical distribution-free framework for coverage guarantees.
REMORA implements Mondrian phase-stratified conformal calibration for the
ordered phase, and a CRC-inspired weighted empirical selective router
\cite{angelopoulos2022crc} with importance weights (following weighted
conformal prediction under covariate shift \cite{tibshirani2019conformal})
for the critical phase (\S\ref{sec:crc}). The exchangeability violation in
the critical phase is documented as a negative result
(\S\ref{sec:negative}). Conformal methods have since been brought to LLM
outputs directly: conformal factuality guarantees via claim back-off
\cite{mohri2024conformal} and conformal abstention for hallucination
mitigation \cite{yadkori2024abstention}; REMORA's contribution is narrower
and different in object: phase-stratified calibration over multi-oracle
governance observables for \emph{action gating}, not per-output factuality.

\subsection{Prover-Verifier Games}
Kirchner et al.\ (2024) \cite{kirsch2024prover} showed that prover-verifier
\emph{training} games improve LLM output legibility by requiring provers
to justify claims to iteratively trained verifiers. REMORA does not
implement that training game; it borrows the framing for a PVD-inspired
offline agreement score, using Semantic Entropy clustering to select the
prover (dominant-cluster oracle) and verifier (independent challenger)
from already-produced responses, without additional API calls
(\S\ref{sec:pvd}).

\subsection{AI Governance and Policy-as-Code}
Algorithmic-audit scholarship emphasizes institutionalized third-party
oversight and audit-system design \cite{raji2022outsider}; Raji et al.\
identify lack of audit data access as the most significant vulnerability
of the current AI audit ecosystem. REMORA's DecisionEnvelope addresses
this access gap by logging each governance decision in a tamper-evident hash
chain, which detects edits but not a full rewrite (\S\ref{sec:audit}), and the Replay Engine publishes governance episodes for
third-party inspection. The EU AI Act (2024) \cite{euaiact2024} mandates human oversight and
audit trails for high-risk AI systems. Open Policy Agent (OPA)
\cite{opa} provides a production-grade Rego policy engine. REMORA
ships an OPA adapter as a concrete instantiation of policy-as-code for
AI decisions; on OPA unavailability it falls back to the parity-tested
deterministic Python policy engine and records the fallback, without
bypassing policy enforcement. The reference
API currently invokes the Python engine directly (\S\ref{sec:architecture}).

\subsection{Assurance Cases}
Kelly (1998) \cite{kelly1998goal} and Bloomfield \& Bishop (2010)
\cite{bloomfield2010safety} structure safety arguments as
claim-evidence-reasoning trees. REMORA's DecisionEnvelope is designed
to populate one node of such a case with a specific gate decision's
evidence chain.

\subsection{Human-in-the-Loop / Human-on-the-Loop}
Endsley (1995) \cite{endsley1995toward} provides the
situation-awareness theory underpinning human supervision of dynamic
systems; the automation-oversight literature distinguishes
human-in-the-loop confirmation from human-on-the-loop monitoring.
REMORA's four-outcome schema implements this
spectrum: \textsc{accept} (human-on-the-loop) through
\textsc{escalate} (human-in-the-loop), with \textsc{verify} and
\textsc{abstain} as intermediate states.

\subsection{Industrial AI Safety}
The oil-and-gas sector has established quantitative risk frameworks
(NORSOK D-010:2021 \cite{norsok2021d010}; IEC 61511:2016 \cite{iec61511})
that define action classes requiring human sign-off. REMORA's case study
(\S\ref{sec:casestudy}) uses this domain as an illustration of how
policy-gated AI governance maps to existing industrial safety
requirements. No domain-specific correctness is claimed.

\subsection{Runtime Guardrails: Agent Permissioning, and AI Control}

\paragraph{Content guardrails.}
Llama Guard and its successors \cite{inan2023llamaguard} classify
conversational inputs/outputs against a safety taxonomy; NeMo Guardrails
\cite{rebedea2023nemo} provides programmable dialogue rails;
Constitutional Classifiers \cite{sharma2025constitutional} defend against
universal jailbreaks with classifiers trained on constitution-generated
data; Rule-Based Rewards \cite{mu2024rules} move safety rules into
training. These systems govern \emph{content}; REMORA governs
\emph{actions}: its unit of decision is a proposed tool call with
operational consequences, and its deterministic hard-block layer is, by
design, not overridable by any learned component. A trained classifier
and a policy floor fail differently, and REMORA's position is that action
gating in consequential environments needs the latter beneath the former.

\paragraph{Agent-level guardrail systems.}
LlamaFirewall \cite{chennabasappa2025llamafirewall} is the closest
industrial system in scope: a layered agent guardrail (prompt-injection
detection, alignment checking, code screening). GuardAgent
\cite{xiang2025guardagent} generates guardrail code with a guard LLM;
AgentSpec \cite{wang2025agentspec} defines a DSL of runtime
triggers/predicates/enforcement near-isomorphic to REMORA's policy
invariants. Two 2026 systems share REMORA's learning ambition: AgentTrust
\cite{yang2026agenttrust} splits threats into lexical (deterministic
rules) and semantic (LLM judge with a guarded verdict cache), and
\emph{self-distills judge decisions into its rule layer}; Membrane
\cite{choi2026membrane} evolves a contrastive safety memory against
jailbreaks. REMORA's differences are deliberate: (1) the hard-block floor
is fixed, versioned, and hash-provenanced policy-as-code, learned outputs
never become enforcement rules, and the learning layer (AROMER) is
monotonicity-tested to \emph{never weaken} policy
(\path{tests/policy/test_governance_intelligence_never_weakens_policy.py}),
whereas AgentTrust's distillation pipeline makes learned judgments
load-bearing for enforcement; (2) on the research path uncertainty is
structural (multi-oracle disagreement with conformal abstention), not a
single judge's confidence, while on the governed path these signals are
left unset and decisions rest on deterministic policy
(\S\ref{sec:observables-limits});
(3) every decision emits a DecisionEnvelope, which the API path
finalizes into a tenant-scoped hash chain and HMAC-signs when a signing
key is configured.
Conversely, AgentTrust reports zero benign hard-blocks across 45{,}000
actions, the opposite end of the safety/friction trade-off from REMORA's
FBR=100\% AgentHarm corner point (\S\ref{sec:agentharm}), and an explicit
target for REMORA's calibration roadmap.

\paragraph{Permissioning and security by design.}
Progent \cite{shi2025progent} enforces programmable least-privilege on
agent tool calls. With LLM-generated policies and gpt-4o it reduces
attack success on AgentDojo from 39.9\% to 1.0\%, at 76.3\% utility
against 79.4\% undefended (arXiv:2504.11703v2; v3 repeats the 39.9\% to
1.0\% figure, v1 reported 41.2\% to 2.2\%). CaMeL
\cite{debenedetti2025camel} defeats prompt injection by construction via
control/data-flow separation and solves 77\% of AgentDojo tasks, against
84\% undefended, with what the authors call provable security
(arXiv:2503.18813v2; v1 reported 67\%). These results define the current (safety, friction)
frontier and pre-empt any reading of REMORA's zero-FAR corner point as
sufficient. REMORA's own execution chain
(\S\ref{sec:execution-chain}) is capability-based enforcement of the same
family, applied per call. Unlike CaMeL it does not track data flow, so it
does not stop an exfiltration composed of individually authorized calls
(\S\ref{sec:negative}). Its contribution is not the corner but the
integrated chain and the claim-governed evaluation around it.

\paragraph{Information-flow control and isolation.}
Information-flow control addresses the case per-call authorization
leaves open: an exfiltration built from individually authorized calls.
Wu et al.\ (2024) \cite{wu2024fsecure} build an f-secure LLM system in
which a security monitor keeps untrusted input out of the planning
process, with formal models of the guarantee. FIDES
\cite{costa2025fides} is a planner that tracks confidentiality and
integrity labels and enforces policies deterministically; the authors
characterize which properties dynamic taint-tracking can enforce.
IsolateGPT \cite{wu2025isolategpt} (first posted as SecGPT) isolates the
execution of third-party LLM apps from each other and from the system.
REMORA borrows the premise that untrusted data must not decide what runs.
It does not propagate confidentiality or integrity labels across calls,
has no separate planner, and claims no trajectory-level or data-flow
property (\S\ref{sec:negative}). These systems are the baselines a
data-flow extension of REMORA would have to be measured against.

\paragraph{Prompt-injection defenses.}
A second family hardens the model or the agent loop. Spotlighting
\cite{hines2024spotlighting} transforms untrusted input so that its
provenance stays visible to the model. StruQ \cite{chen2025struq}
separates prompt and data into two channels and fine-tunes the model to
follow instructions only in the prompt channel. SecAlign
\cite{chen2025secalign} pursues the same goal with preference
optimization. Task Shield \cite{jia2025taskshield} checks at test time
whether each instruction and tool call serves the user's goal. MELON
\cite{zhu2025melon} re-executes the trajectory with a masked user prompt
and flags an attack when the original and masked runs propose similar
actions. Conseca \cite{tsai2025conseca} generates just-in-time,
contextual and human-verifiable security policies, where REMORA's
hard-block floor is fixed and versioned (\S\ref{sec:decision}).
Beurer-Kellner et al.\ (2025) \cite{beurerkellner2025patterns} propose
design patterns for agents with provable resistance to prompt injection
and analyze their utility and security trade-offs. REMORA does not train
models, transform prompts or re-execute trajectories. It acts at the
tool-call boundary after the model has proposed an action, so these
defenses sit upstream of it, and REMORA reports no measurement against
any of them.

\paragraph{Benchmarks and environments.}
Beyond AgentHarm \cite{andriushchenko2024agentharm}, the field evaluates
on AgentDojo \cite{debenedetti2024agentdojo}, ToolEmu
\cite{ruan2024toolemu}, InjecAgent \cite{zhan2024injecagent}, R-Judge
\cite{yuan2024rjudge}, and $\tau$-bench \cite{yao2024taubench}. ToolEmu's
LM-emulated sandbox anticipates the counterfactual-execution idea behind
REMORA's Shadow Mode; REMORA's replay engine is therefore \emph{not}
conceptually unique: its distinction is the governance framing (committed
replay artifacts under claim governance). Replication of REMORA's results
on these independently constructed environments is required future work
and the honest boundary of every internal benchmark claim in this paper.

\paragraph{AI control.}
Greenblatt et al.\ (2024) \cite{greenblatt2024aicontrol} formalize safety
protocols that remain effective when the policy model itself is
intentionally subversive, using trusted monitoring with a limited audit
budget. REMORA is related to the trusted-monitoring protocols of that
taxonomy and adds a deterministic trusted floor. The hard-block layer and
the authority-bound
execution chain are the trusted components, the oracle swarm is a set of
weaker trusted monitors, and \textsc{escalate} spends the audit budget. Two
properties of the design are the control-relevant ones. Within the declared
custody profile the untrusted agent never holds the material that mints
authority, and no model output, its own or a monitor's, can clear a hard
block. Resampling and defer-to-trusted protocols from the control literature
are implemented as a library (\path{remora/governance/control_protocols.py},
roadmap item RF-04) and are not wired into the decision path.
Section~\ref{sec:threat-model} states the threat model. A strategically
subversive agent, collusion between monitors and monitor evasion remain
open items for the red-team plan, and the benchmarks in
\S\ref{sec:results} do not measure them.

\paragraph{Regulatory operationalization.}
COMPL-AI \cite{guldimann2024complai} provides a technical interpretation
of the EU AI Act as model-level benchmarks; REMORA operationalizes a
complementary slice at runtime, Article 12 (logging) via the
DecisionEnvelope hash chain, Article 14 (human oversight) via
\textsc{verify}/\textsc{escalate} routing, without claiming conformity
assessment.

\paragraph{Multi-layer guardrail taxonomies.}
A systematic literature review of runtime guardrails
\cite{shamsujjoha2024taxonomy} frames multi-layer defense as a
Swiss-cheese model; a layered governance architecture with OS-level
enforcement is developed in Ge (2026) \cite{ge2026governance}; confidence
elicitation by fidelity is treated in Zhang et al.\ (2024)
\cite{zhang2024fidelity}; and formal verification of behavioral safety
properties for neural policies in Corsi et al.\ (2021)
\cite{corsi2021formal}. REMORA's position relative to these four is that
it composes recognized layers (policy floor, ensemble uncertainty,
conformal abstention, audit chain) with a claim-governance methodology,
rather than introducing a new layer type.

\paragraph{Authority-bound execution and execution evidence.}
A 2026 line of work moves the control point from pre-action screening to
the authorization and evidence of execution itself. AIRGuard
\cite{qin2026airguard} names \emph{authority confusion} (untrusted
context may inform reasoning but must not authorize side effects), a form
of the confused-deputy problem \cite{hardy1988confused}, and
enforces least privilege as action-time authorization. Proof-Carrying
Agent Actions \cite{wang2026pcaa} organizes runtime-neutral governance
around a portable action certificate with five checkpoints, from
pre-action admissibility through approval to outcome closure. Proof of
Execution \cite{rhodes2026poe} formalizes execution evidence as a
contract, a causal event stream and a replay context with
validator-checkable invariants and a soundness argument under explicit
cryptographic and deployment assumptions. A survey of agent permission
systems \cite{michael2026permission} reviews 21 proposals and finds
that none of them achieves all three of low user burden, formally
grounded specification and deterministic enforcement. REMORA's position rests on
explicit \textbf{non-claims}: it is not first with runtime policy
enforcement, pre-action authorization checks, or agent governance in
general. What it combines in one reproducible artifact is authority
provenance (signed ToolSpec), exact-call binding between approved and
executed action, key-custody separation between decision and execution
domains, re-policying at the execution boundary, per-component
trust-base coverage declared on the decision record, explicit
effect-evidence states in which transport success is never execution,
machine-readable capability and boundary declarations whose claim
ceilings state what is not established,
and a machine-enforced register of claims and negative results
governing the headline numbers reported here. A mechanism-level crosswalk is
maintained in the repository
(\path{docs/research/adjacent-systems-crosswalk-v2.md}).

\paragraph{Protocols, authorization tokens and policy languages.}
The Model Context Protocol specification \cite{mcp2025spec} standardizes
how hosts expose tools to models. It states that MCP ``cannot enforce
these security principles at the protocol level'' and that tool
annotations ``should be considered untrusted, unless obtained from a
trusted server''. REMORA takes the same position on tool metadata: an
approval binds to a signed ToolSpec (\S\ref{sec:execution-chain}), not
to what a server declares. Capability tokens with caveats
\cite{birgisson2014macaroons} and Biscuit \cite{biscuit2026}, whose
holders attenuate tokens offline and whose checks are written in
Datalog, are the token-level precedents for REMORA's exact-call lease.
OAuth Rich Authorization Requests \cite{lodderstedt2023rar} carry
structured \texttt{authorization\_details} that a scope string cannot
express, close in intent to binding a lease to one call. XACML~3.0
\cite{oasis2013xacml} defines the policy decision point and policy
enforcement point vocabulary that \S\ref{sec:execution-chain} uses.
Cedar \cite{cutler2024cedar} is an authorization language whose design
properties are proved in Lean. REMORA uses none of these formats or
languages on the wire; its policies are Python with an OPA/Rego adapter
(\S\ref{sec:decision}). Binding grants to the task and the exact call
is aimed at the confused-deputy problem \cite{hardy1988confused}.

\paragraph{Tamper-evident logs.}
Schneier and Kelsey \cite{schneier1999secure} make log entries written
before a logging machine's compromise unreadable to the attacker and
impossible to change or delete undetectably. Crosby and Wallach
\cite{crosby2009tamper} give tamper-evident history trees with efficient
membership and consistency proofs, and Certificate Transparency
\cite{laurie2013ct,laurie2021ct} publishes append-only Merkle-tree logs
that third parties audit. REMORA's audit chain is a per-tenant SHA-256
hash chain (\S\ref{sec:audit}). It detects modification of a historical
entry but not replacement of the whole chain. It has no forward-secure
keying and is not anchored in an external log; these works are what a
hardened chain would borrow from.

\section{Problem Statement}
\label{sec:problem}

Let $\mathcal{A}$ be a space of agent-proposed actions, $q$ a query,
and $c = (\text{domain}, \text{risk}, \text{env})$ an operational
context. We seek a control function:
%
\begin{equation}
\begin{split}
\Gate: (q, a, c) \;\longrightarrow\; g, \qquad\qquad\\
g \in \{\textsc{Accept}, \textsc{Verify}, \textsc{Abstain}, \textsc{Escalate}\}
\end{split}
\end{equation}
%
with five required properties: (1)~safety-first (hard policy violations
map to \textsc{Escalate} regardless of consensus); (2)~calibration-aware \cite{guo2017calibration}
(abstain when uncertainty exceeds threshold); (3)~evidence-sensitive
(evidence can resolve or contradict ambiguous consensus);
(4)~auditable (every call produces a hash-chained evidence record,
HMAC-signed when a signing key is configured);
(5)~conservative by default (fail closed toward \textsc{Verify} or \textsc{Escalate} depending on risk tier).

This is not a question of oracle \emph{accuracy}: REMORA does not
know whether action $a$ is correct. It is a question of
\emph{assurance conditions}: whether the conditions that justify
autonomous execution of $a$ are verifiably met.

\subsection{Threat Model}
\label{sec:threat-model}

This subsection states the adversary and the trusted computing base that
the execution-chain claims assume. It draws on
\path{docs/assurance/threat_model_v1.md}, a STRIDE baseline written before
the execution layer existed, and on the code paths named in
\S\ref{sec:execution-chain}.

\paragraph{Attacker position.} The attacker is the agent, or content that
steers the agent, for example through prompt injection. It acts only by
proposing calls at the gate: a tool name, arguments, and any labels that
accompany them. It holds no signing key and cannot edit the tool registry
or the policy bundle. The model assumes it reaches tools only through the
governed dispatcher; paths that bypass the dispatcher are out of scope.

\paragraph{Trusted computing base.} The claims hold only if four parties
are trusted. The ToolSpec author signs the specification that defines what
an approval covers. The policy author owns the versioned bundle that the
PDP and the PEP evaluate. The intent source is the deployment component
that supplies or verifies the task intent and the tool contracts. Key
custody covers the domains that hold the PDP signing key and the Ed25519
lease key, which the agent never holds (\S\ref{sec:execution-chain}). The
policy code, the dispatcher and the audit store belong to the same base,
and a compromise of any of them is out of scope.

\paragraph{Labels supplied by the agent are untrusted.} A risk tier,
action type or task intent that arrives with a proposed call is a claim,
not authority. Where the opt-in enrichment stage runs, an inferred higher
risk overrides a supplied lower label and never the reverse
(\S\ref{sec:gov_intel}). Untrusted content that controls a sensitive argument
escalates whatever risk tier the caller declared
(\texttt{hard\_guard\_floor()}). A model may propose a task intent, but
its clauses count only where their quoted spans occur in the task text
(\S\ref{sec:wrongcall-implication}).

\paragraph{Argument content and destinations.} The attacker chooses every
argument value, including URLs, recipients and payload text. The decision
reads the tool name, the registry's labels and the call's binding. It does
not read what an argument carries or where a call sends it. A low-risk read
whose URL carries a secret is therefore within the attacker's reach and is
not defended. An argument-content and destination policy has to come from
the information-flow check (\texttt{remora.flow}), and no decision reads
its verdict yet (\S\ref{sec:negative}).

\paragraph{Injection patterns are a hint.} The admission firewall escalates
a few known injection phrasings by substring match. A paraphrase passes it,
so the list is a routing hint, not a security boundary. An injection is
judged by what the injected call can reach. A run on an external injection
benchmark is pre-registered and not done.

\paragraph{Out of scope.} The model does not cover calls that bypass the
governed dispatcher through alternate credential, network or execution
paths, or privileged effects that an authorized tool's implementation can
reach (\S\ref{sec:boundary-declarations}). It does not cover exfiltration
through an authorized call's arguments, or composed of individually
authorized calls, because REMORA does not track data flow
(\S\ref{sec:related}). A strategically subversive agent,
collusion between monitors and monitor evasion are open items for the
red-team plan. Compromise of the host, the keys, or the ToolSpec, policy
or intent sources is excluded, as are availability attacks such as
rate-limit exhaustion. Section~\ref{sec:negative} reports a post-hoc
evaluation of the chain within this model.

\section{REMORA Architecture}
\label{sec:architecture}

REMORA processes each gate request through six decision stages,
followed by DecisionEnvelope emission (Stage~7).
The architecture diagram in the supplementary material (Mermaid) shows
the full pipeline. Stage~7 is the output record, not a decision stage.

\paragraph{Stage 1: Intake \& Risk Classification.}
The system classifies intent domain, risk tier
($\in\{$low, medium, high, critical$\}$), action type, and target
environment. An adversarial admission firewall checks for injection
patterns (``ignore previous instructions'', ``drop table'', etc.) and
fires an immediate \textsc{Escalate} if detected.

\paragraph{Stage 2: Oracle Fan-Out.}
$n$ configured oracle models are queried in parallel
via \texttt{ThreadPoolExecutor} (the engine accepts $n \geq 2$; the
design recommendation is $n \geq 3$ from distinct model families. The
2026-07 clean round and AgentHarm use a Cloudflare Workers AI cross-family
trio (Meta LLaMA, Qwen, Mistral) enforced by
\texttt{remora/oracles/families.py}; earlier rounds used a Groq
three-LLaMA swarm whose within-family correlation gave an effective
diversity closer to two). Responses with
non-null \texttt{error} fields are excluded before any aggregation.
$\OraclesV \subseteq \Oracles$ denotes the valid oracle set.

\paragraph{Stage 3: Canonicalization \& Weighted Consensus.}
Each response is canonicalized by $\varphi: \mathrm{raw} \rightarrow v$
where $v$ is the tuple (\texttt{polarity}, \texttt{claim\_hash},
\texttt{magnitude}, \texttt{tags}).
The \texttt{claim\_hash} field uses a pluggable backend: the default
\texttt{TokenFingerprintBackend} applies a 16-char SHA-256 truncation over
NFKC-normalized sorted tokens for backward-compatible, dependency-free
operation; the \texttt{NLISemanticBackend} replaces this with bidirectional
cross-encoder entailment clustering, implementing Semantic Entropy
\cite{kuhn2023semantic}. Oracle weights are derived from
inverse pairwise correlation (Appendix~\ref{app:consensus}).

\paragraph{Stage 4: Consensus Observables.}
Entropy $H$ is computed over the diversity-weighted verdict distribution
$\hat{p}$. The \texttt{NLISemanticBackend} grounds $H$ as Semantic
Entropy~\cite{kuhn2023semantic},
$\mathrm{SE}(x) = -\sum_{c \in \mathcal{C}} p(c\,|\,x)\log p(c\,|\,x)$
over NLI-derived semantic equivalence clusters $\mathcal{C}$.
\emph{Note on experimental backend:} all benchmarks reported in
\S\ref{sec:eval} use the default \texttt{TokenFingerprintBackend}
(NFKC-normalised, sorted-token SHA-256 truncation), which approximates
cluster identity via lexical overlap. The NLI backend is a
drop-in replacement for future work but was not used in the
reported results; claims about Semantic Entropy properties should
be read accordingly.
Dissensus $D$, consensus concentration $\eta$ and trust score
$\trust$ are computed (Appendix~\ref{app:consensus}), and a regime
$\in\{\text{ordered}, \text{critical}, \text{disordered}\}$ is
assigned. These run on the research and benchmark path; the governed
server routes leave them unset (\S\ref{sec:observables-limits}).

\paragraph{Stage 5: Evidence Router (Critical Phase).}
If phase = critical, the \texttt{CriticalEvidenceRouter} evaluates a
five-field \texttt{EvidenceSignal} and returns one of:
\texttt{evidence\_accept}, \texttt{abstain}, or \texttt{escalate}.
\emph{Important:} the current EvidenceSignal is an oracle-proxy
(built from consensus statistics); semantic BM25/NLI retrieval is
pluggable but not live (\S\ref{sec:evidence}).

\paragraph{Stage 6: Policy Engine.}
Seven \emph{headline} policy controls are evaluated in priority order
before any routing logic; the shipped engine's complete priority-ordered
gate inventory is larger (schema, forbidden-tool, coercion, tainted-argument,
rollback, production-write, quorum, trap-detection, session/fleet-risk
gates, among others) and is maintained in
\path{remora/policy/decision_engine.py}, with \texttt{hard\_guard\_floor()}
as the single deterministic floor no probabilistic result can override. An OPA/Rego adapter with Python fallback is implemented and
parity-tested, but the reference API invokes the Python policy engine
directly; OPA remains an integration option and production dependency
(fail closed either way). Gate outcome $g$ is assigned.

\paragraph{Output: DecisionEnvelope v2.}
An attribute-frozen envelope (treated as read-only; nested collections
are not deep-frozen) records: request, assessment, gate, reviewer
context, follow-up request, case history, policy-learning candidate,
and audit hash-chain entry.


\subsection{The Authority-Bound Execution Chain}
\label{sec:execution-chain}

Deciding and executing are separate trust domains, bound with
cryptographic identity at every hop. The policy layer issues a
\texttt{PolicyDecisionToken} (format v3: Ed25519 over a domain-separated
payload, with a key identifier derived from the public key; the observation
hash binds it to one governance call; the \texttt{jti} is consumed exactly
once against a durable ledger, and an in-memory database is refused as a
``durable'' backend). A redeemer configured with verification keys alone
verifies every grant it is shown and mints none. The HMAC formats v1 and v2
remain readable; once Ed25519 material is configured they are refused as
live authority unless a migration window is declared. What an approval is granted \emph{over} is a signed ToolSpec
whose identity travels inside the lease; a spec that moved between
approval and dispatch refuses. Dispatch itself happens only under an
exact-call \texttt{ExecutionLease} (tenant, actor, tool, canonical
argument hash, target, policy-bundle identity, single-use nonce,
expiry), signed with Ed25519 under an architectural custody split
claimed within the strict governed-execution profile under the declared
credential topology: the
authority domain holds the private key and no declared downstream tool
credential; the
execution domain holds the public key and the declared execution
credentials. The
\texttt{GovernedToolDispatcher} re-verifies the entire binding against
the concrete call, against the clock the lease was issued under, before
anything runs. The split does not establish the absence of alternate
credential, network or execution paths that bypass the governed
dispatcher; that boundary is stated explicitly in
\S\ref{sec:boundary-declarations} and \S\ref{sec:negative}. Authorization and result are separate hash-chained
records, each carrying the per-component trust-base view resolved at
that moment: the closure record re-reads rather than copies, so a
stale policy snapshot is detectable as a failed component-level join. A
crash-consistent outbox records dispatch intent before the effect and
reconciles stranded dispatches to \textsc{unknown}; effect verification
is a separate, replay-protected receipt. For principal revocation, the
audit event joins the state transaction through an audit outbox and is
projected on a later execution-path interaction; this does not imply
that all API audit writes are transactional or that idle tenants are
automatically swept. \textbf{Stated gaps:} the
decision/enforcement split is real only where \texttt{/assess} and
\texttt{/execute-accepted} run in different custody domains. A deployment
that runs both in one process with the private key is one domain, and the
review path still mints and consumes in-process. No deployment is proven to
configure the asymmetric grant (RMR-CR-002 stays partial). KMS/HSM key
management and process-boundary mTLS are not implemented; dispatch runs in the API process by default, with
an opt-in separated dispatch worker (202 after durable authorization;
the worker half re-verifies the persisted call against the recorded
binding) exercised so far only by CI and its contract tests.

\subsection{The Argument-Resolution Ladder}
\label{sec:resolution-ladder}

The six stages above describe how an action reaches a verdict. They do not
describe what the engine reasons about when the action is well-formed but the
\emph{state it refers to} is uncertain, which, in operational deployments,
is the common case. That reasoning is a distinct ladder, evaluated after every
blocking gate so it can only ever make a would-be \textsc{accept} more
cautious, never unblock one:

\begin{enumerate}\setlength{\itemsep}{1pt}
\item \textbf{Authoritative tool metadata.} Effect, risk class, resource type
  and validator bindings come from a server-side registry. A caller may raise
  risk, never lower it. Verb heuristics are a fallback for unregistered tools
  only, a lesson learned when \texttt{assign}, \texttt{close} and
  \texttt{approve} were absent from a mutating-verb list and thirty writes
  scored as reads.
\item \textbf{Coverage declaration.} A state index may not infer its own
  completeness. Closed-world authority is a signed, curator-bound declaration
  scoped per argument role, with a snapshot hash, an as-of date and a
  freshness bound. Without it, absence means \textsc{unknown}.
\item \textbf{Tenant, hash and freshness binding.} A declaration that does not
  match the snapshot it claims, or that has aged past its bound, is refused
  rather than trusted. Cross-tenant consultation is refused outright.
\item \textbf{Argument support.} Does the system of record contain this value?
  Tri-state: present, confirmed absent, or outside coverage. Unknown must
  never behave like a negative.
\item \textbf{Value grounding.} Are the argument values traceable to
  \emph{this} task: named in the task text, declared by the tool's own
  schema, or vouched for by the system of record? A call whose values anchor
  to nothing here is observationally a foreign call.
\item \textbf{Validation requirement.} An argument that steers where the action
  lands must be confirmed before autonomy, decided by what the argument
  \emph{does} rather than by whether an index happens to cover it.
\item \textbf{Resolver availability.} If a bounded lookup can close the gap, the
  verdict is \textsc{verify} carrying a \texttt{ResolutionPlan} that names the
  resolver, the exact arguments it may write, and the sources permitted to
  supply them. If no resolver exists, the verdict is \textsc{abstain}:
  promising a verification that cannot happen is worse than stopping.
\item \textbf{Validator execution and full re-entry.} The resolver returns one
  value and hands control back. It never performs the original call and cannot
  redirect it. The \emph{whole} router then re-runs on a fresh observation, so
  every guard applies again to the resolved call rather than being patched
  around.
\item \textbf{Read/write posture.} A verified read may proceed autonomously; a
  write does not, whatever the state evidence says.
\end{enumerate}

This ladder, not the consensus machinery, is what the operational results in
\S\ref{sec:routing-blind}--\S\ref{sec:wrongcall-implication} measure. Its
tri-state discipline is the recurring commitment: \textsc{unknown} is a first-class
verdict distinct from \textsc{unsupported}, and a signal that cannot be established
is left absent rather than guessed, since a fabricated boolean enters the policy
contract as fact, while \texttt{None} correctly says nothing establishes this.

\subsection{Evidence Admission, Federation and Standards Work}
\label{sec:federation}

A separate, tested \texttt{remora/evidence/admission/} module derives
producer visibility, coverage, observation vantage, exact-invocation binding
and prior-commitment premises from typed records and deployment-owned trust
configuration. Malformed evidence is a processing failure, not a negative
property verdict. The module does not feed the frozen conformance checkers,
effect verification or the execution decision; it supplies a contract for
evaluating the provenance of future observations. Its six clauses follow
the evidence-sufficiency premises of the CoSAI workstream on secure design
of agentic systems (WS4, \S7.4; \path{docs/design/evidence-admission-v1.md}).
\texttt{NOT\_ESTABLISHED} is a conclusion reached after verification ran;
malformed input is a processing failure; self-report is not independent
observation. Absence needs producer visibility and coverage for the same
scope; identifier equality is not binding; expected verdicts stay outside
admission inputs. The author took part in the workstream's public
request-for-comment threads on agent manifests and on evidence
sufficiency.\footnote{cosai-oasis/ws4-secure-design-agentic-systems
issues \#149, \#189 and \#27, August to September 2026.} Those threads
argued the boundary between attested deployment state and action-time
authority, and the three-valued verdict for absent evidence. The repository's
evidence-sufficiency conformance packages are research artifacts, not
workstream deliverables.

Federation packages pin source revisions and file digests, preserve native
claim vocabulary and distinguish reproduction from an independent second
implementation. External run records exist for the exact-call-binding,
fresh-authority and effect-evidence contracts (E-ECB, E-FA, E-EE). They were
run by an external second implementation (Probity) against frozen fixture
packages and are recorded as \texttt{NOT\_INDEPENDENT}, with each
boundary-level claim result \texttt{NOT\_ESTABLISHED}. The E7
runtime-surface contract has two external Probity run records (2026-10-08
and 2026-10-09) that meet the repository's recorded independence rule, so
its lifecycle is \texttt{EXTERNALLY\_VERIFIED} with independence
\texttt{INDEPENDENT}. That rule means a second implementation importing no
producer code, run outside the producer's control; it is not a blind study.
The record keeps its exposure: the expected answers were published before
the reader was written, and a lint diagnostic later exposed parts of the
retained reference verifier. The reader neither imported nor executed it. Both records establish fixture premises only; the claim result
and runtime capability-surface completeness stay \texttt{NOT\_ESTABLISHED}
(\path{artifacts/interop/index.json}, \path{docs/interop/FEDERATION.md}).

The federation work also runs in the other direction. A contract-coverage
map lists every normative rule of the federation-port transport's contract
with the tests that exercise it, and 29 contract probes run against the
unmodified upstream runtime. The probes found four findings (CP-F1 to
CP-F4). A late provider confirmation was dropped from operation state under
lease takeover, and a deadline did not bound first provider contact.
Unbounded adapter reason text entered provenance, and a lost response under
outage closed an operation as failed while a refund existed. The
fourth was found by a TLA+ model of lease retry
(\path{formal/tla/LeaseRetry.tla}, checked in CI) and replayed by a probe.
All four were fixed upstream in a pull request from this repository
(aeoess/federation-port\#1, merged 2026-10-08); the probes now assert the
corrected behaviour and fail on the pre-fix runtime
(\path{artifacts/interop/federation-port-v0/contract-coverage.json}).
Federation records are evidence references, never execution authority. On
the enforcing API, typed semantic judgments from an external provider are
opt-in shadow records appended after audit; they can guide a lookup or an
approver but do not change a verdict.

\subsection{Machine-Readable Capability and Boundary Declarations}
\label{sec:boundary-declarations}

The properties above are published as machine-readable declarations,
not only as prose. \path{docs/interop/remora-capabilities-v1.yaml}
declares each workflow capability with its stage in the chain from
authority through dispatch to effect. It records the roles a capability
provides and does not provide, its trust assumptions, its maturity
level, its evidence links and its limitations. Maturity runs from
\texttt{DECLARED} to \texttt{OPERATOR\_OBSERVED}; no declared capability
currently claims the external or operator-observed states.
\path{docs/interop/remora-boundaries-v1.yaml} declares the internal
trust boundaries, external interfaces and Federation edges as separate
records. Each is bound to a named \textbf{claim ceiling}: a bounded
statement of what the record establishes, paired with explicit
non-claims. Federation edges carry separate \textbf{status dimensions}
for owner confirmation, pinning, execution, independence, claim result,
production evidence and Federation adoption. A recorded external run
advances the execution and independence dimensions only under the record's
stated rule, and never the claim-result, production or adoption dimensions
by itself. Role mappings for the draft Agent Authority
Conformance model are declared as candidates with their partial
coverage stated.

The declarations are fail-closed in both directions. CI gates fail
when a declaration diverges from the assurance registers, the pinned
source revisions or the recorded evidence digests:
\path{scripts/check_remora_capabilities.py},
\path{scripts/check_remora_boundaries.py} and
\path{tests/test_remora_boundary_declaration.py}. A boundary cannot
claim higher maturity than the capabilities that support it. Three
properties are declared precisely because they are \emph{not}
established. All three are listed under
\texttt{unestablished\_properties} in
\path{docs/assurance/capability_register_v1.yaml}; the boundary
declaration carries the first as its global property:

\begin{itemize}
\item \textbf{Runtime capability-surface completeness}
  (\texttt{runtime\_capability\_surface\_completeness},
  \texttt{NOT\_ESTABLISHED}): the reference runtime observes its own
  offered tool surface and dispatcher. This does not establish
  completeness for external agent processes, host credentials or
  unobserved alternative paths. Calls that bypass the governed
  dispatcher are outside the boundary by declaration.
\item \textbf{Implementation effect non-transitivity}
  (\texttt{implementation\_effect\_non\_transitivity},
  \texttt{NOT\_ESTABLISHED}): authorization of a tool does not
  authorize every privileged effect its implementation can reach. An
  exact-call lease binds the call, not the implementation's reachable
  effect space. The three-domain mediation split whose effect domain
  alone holds the declared effect credentials is implemented (CAP-024),
  but no deployment runs it, so the property remains open.
\item \textbf{Authoritative execution-context binding}
  (\texttt{execution\_context\_authoritative\_binding},
  \texttt{NOT\_ESTABLISHED}): an opt-in path binds the
  deployment-supplied subject, the proposal-initiating model, the scoped
  data classification and build/runtime provenance through assessment,
  review, grant, lease, dispatch and effect recording. Its tests do not
  establish that the deployment sources of that context are
  authoritative, nor a deployed end-to-end property.
\end{itemize}

These three declarations define the reader-facing scope of every custody
and dispatch claim in this paper. REMORA establishes properties
\emph{at} a declared boundary, and the declarations say where that
boundary ends.

\section{Governance Intelligence Layer: Misspecification-Aware Pre-Policy Enrichment}
\label{sec:gov_intel}

The policy engine is only as honest as the metadata it is given: an
integration bug, or a compromised agent, can label a destructive
action as a low-risk read and present the gate with nothing to fire
on. Added at package version 0.9.0 (repository tag \texttt{review-v1}), the \emph{Governance Intelligence
Layer} (\path{remora/governance_intelligence/}) closes this gap with
an opt-in, fully deterministic enrichment stage that runs before any
policy rule (no LLM calls): (1)~fail-closed normalization of
caller-supplied labels (unknown is explicit, never coerced to a safe
value); (2)~action-semantics extraction from the proposed action text
and tool metadata; (3)~misspecification-risk inference from
label/semantics disagreement; (4)~causal-consequence signals \cite{bjoru2026causal,pearl2009causality} (blast
radius, expected loss); and (5)~policy-generalization risk, would
repeatedly accepting this \emph{class} of action remain safe
fleet-wide?

Signals merge into the existing \texttt{PolicyObservation} under a
\textbf{strengthen-only} rule: inferred higher risk may override a
supplied lower label, never the reverse, and hard-block flags are
never cleared. A grid property test across 2{,}160 observation
combinations verifies that enrichment never converts a rejection into
an acceptance
(\path{tests/policy/test_governance_intelligence_never_weakens_policy.py}).
The engine remains the sole decision authority.

\section{Evidence-Grounded Critical-Phase Routing}
\label{sec:evidence}

\subsection{The Critical-Phase Problem}

In the critical phase, oracle consensus is near the phase boundary.
Empirically, higher trust scores \emph{negatively} correlate with
correctness ($n=32$ real-oracle items): Q4 high-trust achieves 50\%
correct; Q1 low-trust achieves 75\% correct. Conformal calibration at
5\% risk target fails completely on critical-phase items (mean
observed risk = 100\%, coverage $\rightarrow 0\%$). Standard trust-based
routing cannot safely gate critical-phase decisions.

\subsection{Offline Selection Components}
\label{sec:crc}

Three offline components are implemented and tested on the research path
and are not invoked by the reference API. The
\texttt{PhaseAwareGuardrail} inverts the trust score for critical-phase
items (Appendix~\ref{app:selection}). A weighted empirical selective
router inspired by Conformal Risk Control does not instantiate the CRC
theorem, so it gives no risk bound (Appendix~\ref{app:crc}). A
PVD-inspired agreement score over already-produced oracle responses
trains no model and makes no model call (Appendix~\ref{app:selection}).

\subsection{CriticalEvidenceRouter}

The router evaluates a five-field \texttt{EvidenceSignal}
with fields (\texttt{evidence\_strength}, \texttt{contradiction\_\allowbreak score},
\texttt{citation\_coverage},
\texttt{cross\_evidence\_\allowbreak consistency},
\texttt{source\_reliability}):

\begin{enumerate}[leftmargin=*,label=\arabic*.]
  \item Coverage gate: \texttt{citation\_coverage}~$< 0.50$ $\Rightarrow$ \textsc{Escalate}
  \item Contradiction block: \texttt{contradiction\_score}~$> 0.50$ $\Rightarrow$ \textsc{Abstain}
  \item Evidence-accept: all thresholds met $\Rightarrow$ \texttt{evidence\_accept}
  \item Default: $\Rightarrow$ \textsc{Escalate} with diagnostic
\end{enumerate}

On MultiNLI ($N=3{,}000$): resolution rate 38.5\%, evidence-accept
precision 100\%, false-accept rate on contradiction items 0\%,
abstain precision on contradictions 99.3\%.

\subsection{Evidence Signal Provenance}

\emph{Current implementation:} \texttt{EvidenceSignal} is built as a
proxy from oracle consensus statistics. This is documented in the
source as a ``structural bridge'' pending semantic retrieval.
\emph{Planned:} external BM25/NLI passage retrieval feeding real
document evidence. The routing logic is fully implemented and tested;
real evidence quality may differ from NLI label quality.

\section{Audit and Governance Envelope}
\label{sec:audit}

\subsection{DecisionEnvelope v2}

Every gate invocation produces an attribute-frozen
\texttt{DecisionEnvelope} (frozen dataclasses treated as read-only;
nested lists/dicts are not deep-frozen) with blocks: request, assessment,
gate, reviewer\_context, follow\_up, history, policy\_learning, and audit.
The library engine emits the envelope with \texttt{previous\_hash} and
\texttt{signature} unset; the API finalizer links the tenant hash-chain
and adds an HMAC signature only when
\texttt{REMORA\_ENVELOPE\_SIGNING\_KEY} is configured.
The full schema is in Appendix~\ref{app:schema}.

\subsection{Audit Hash-Chain}

\begin{equation}
  h_i = \text{SHA-256}(h_{i-1} \;\|\; \mathrm{json}(e_i))
\end{equation}

This provides \textbf{tamper-detection}: any modification breaks the
chain. It does \textbf{not} prevent tampering. Tamper-\emph{proof}
audit requires external append-only storage (S3 Object Lock, Azure
Immutable Blob, or equivalent) as a deployment dependency.

\subsection{Follow-Up Workflow}

\textsc{Escalate} generates a structured follow-up request specifying
reason codes, required evidence, responsible role, and SLA. Data
structures are implemented; production integration with external
ticketing systems is a deployment requirement.

\subsection{What the Wrong-Call Axis Implies}
\label{sec:wrongcall-implication}

The BFCL v4 result is this paper's clearest external routing result:

\begin{quote}
\textbf{Structural validity and semantic correctness are independent
properties, and the governance signals that establish the first cannot
establish the second.}
\end{quote}

Schema validity, argument satisfiability, provenance, taint and value grounding
are all properties of the \emph{call}. Whether the call serves the \emph{task}
is a property of the relation between them, and no amount of scrutiny of the
call alone recovers it. The residue is therefore not a threshold to tune: there
is no threshold on a signal that does not carry the information.

The architecture reserves a slot for the missing authority,
\texttt{tool\_matches\_goal}, tri-state, held at \textsc{Unknown} since
definition rather than filled with a guess. A mechanism now occupies it: a
deployment-declared tool contract (capability, effect, resource type, mutation,
argument roles) matched against a structured task intent, routing an established
contradiction to \textsc{Abstain} for reads and \textsc{Escalate} for writes. It
is placed ahead of trust routing, so a confident consensus cannot execute a call
that the contract shows serves the wrong goal, and behind every hard guard, so it can
never unblock one. The authority limit is the design: a model may \emph{propose}
the intent but may not thereby assert a match, and an intent whose quoted spans
do not occur in the task text yields \textsc{Unknown}, never \textsc{Supported}.

then 0/500 across the structural, contracts-plus-intent and
\textsc{unknown}-floor arms (CLAIM-019). That is a descriptive
single-pass comparison: SAP v5 pre-registered six arms with cluster-level
McNemar tests, and the run implemented three arms and no paired test.
Exact McNemar tests run after the fact give 24 accepts against 0 for the
structural arm against the full configuration ($p = 1.2\times10^{-7}$) and 6
against 0 for contracts-plus-intent ($p = 0.031$); the full configuration
also lost 22 legitimate reads and gained none (NEGATIVE\_RESULTS.md \S83).
Four caveats bound what it measures. The deterministic intent extractor is the
cost carrier: legitimate read autonomy fell to 26.6\% (25/94), far below
the 75\% co-primary bar, so the pre-registered joint hypothesis was not
supported. The denominator counts reads under the frozen bundle's own
classification; over all 487 gold calls arm F accepted 25 (5.1\%). The extractor also ignores negation: ``do not cancel''
supports a cancel call (NEGATIVE\_RESULTS.md \S81). Its heuristic grammar
was designed with spent C-ext2 material visible (SAP v5 \S12, deviation 2). The property
the accept arm establishes is \emph{semantically authorized read}, that the
call is licensed by a declared contract and a re-derived intent, not that it
is the right call for the user's goal. And the result is a routing-bench
measurement: discrimination on the governed execution path, where a live
deployment supplies the intent and contract bundle, remains
\textbf{unmeasured}.

The sealed C-ext4 track measured that price directly. SAP v6 fixed eight
targets before the remaining BFCL v4 reserve was built into 1{,}562 episodes
over 363 clusters, ID-disjoint from every spent population. A revised bundle
(v2, with deterministic derivation receipts) accepted 87/291 = 29.9\% of gold
calls (Wilson 95\% CI 24.9\% to 35.4\%), against 20/291 = 6.9\% for the frozen
C-ext3 bundle on the same episodes. Obtainable \textsc{verify} rose from
45/119 to 100/119 = 84.0\%. Every safety count stayed at zero: native
wrong-call \textsc{accept} 0/295 (Wilson upper bound 1.29\% by row, 5.42\%
over its 67 tools), constructed
wrong-tool 0/119 and required-\textsc{unknown} \textsc{accept} 0/238. All
eight targets were met (CLAIM-021). They were floors, fixed after bundle v2
and its development replays existed; the C-ext3 bars for obtainable
\textsc{verify} (95\%) and read autonomy (75\%) were not carried over. A
refuse-all control arm meets five of the eight: all three safety counts,
irrelevance \textsc{abstain} and unobtainable \textsc{abstain}. Only
gold-call acceptance, obtainable \textsc{verify} and the paired gain over
the frozen bundle separate the arms. Bundle v2 without receipts accepted
84/291, so the receipts add 3 of the 87. The revised extractor handles
negation.

The gain is narrower than that headline. A descriptive split computed after
the run puts 76 of the revised bundle's 87 accepts on the 255 gold calls
whose tool also occurs in the development sets. On the other 36 it accepted
11 against 8 for the frozen bundle. The revisions are naming rules learned
from one tool catalogue, and the reserve shares that catalogue. C-ext4
therefore does not show generalisation to unseen tool families
(NEGATIVE\_RESULTS.md \S82). Of the gold calls, 70.1\% still do not proceed
autonomously. The state
index is empty, so the accepted property is still semantically authorized
read.

A re-analysis run after the peer review (NEGATIVE\_RESULTS.md \S83, post
hoc) narrows the safety reading further. Only 4 of the 295 wrong calls name
a tool the original task offered, so the zero count says almost nothing
about confusing two tools of one task. V2D rejected 137 of them as not
matching the goal and held the other 158 at \textsc{verify} or
\textsc{escalate}, as a refuse-all policy would. Counted by tool, V2D's gain
over the frozen bundle is 19 tools against 2 ($p = 1.1\times10^{-4}$), not
the episode-level $p$ of about $10^{-18}$. Two naive rules, scored on the
same episodes, show how much of the signal is lexical. Accepting when two
tool-name tokens occur in the task accepts 51/291 gold calls and 2/295 wrong
calls, and also 48/238 calls missing a required argument. With one token it
accepts 178/291 gold calls, 6/295 wrong calls and 132/238 calls missing an
argument. V2D accepted 87/291 and none of the others.

No unseen BFCL v4 live row remains, so a test of generalisation needs
a new tool catalogue, sealed before any authoring rule is written for it.

\textbf{Reading the table.} The false-accept column is constant. Every
condition, including the one with the hard blocks removed, records FAR
$=0.000$. An ablation whose conditions do not differ on a metric cannot
identify any component as necessary for that metric, so this ablation
attributes the zero-false-accept result to nothing at all (CLAIM-020).

The \emph{without hard blocks} row is a warning about the metric rather
than merely an inconclusive result. Removing the deterministic floor
leaves FAR at zero while accuracy falls from $0.900$ to $0.300$: the
condition reaches zero false accepts by declining almost every task
rather than by judging it correctly. A refuse-all policy scores perfectly
on false-accept rate, and any measure a degenerate policy also satisfies
is not on its own evidence that a mechanism works.

\textbf{Conclusion.} We report no component attribution for the safety
number from this ablation. What the conditions do separate is task
accuracy and benign review friction, where the hard blocks account for
the largest difference ($0.900 \to 0.300$ accuracy). No ablation whose
conditions differ on false-accept rate has been run, so the deterministic
floor's contribution to the headline safety result is unmeasured.

\textbf{Oracle count.} The exploratory oracle-count ablation on 302 QA
items is in Appendix~\ref{app:oraclecount}. Majority vote over three
oracles beat a single oracle and correlation weighting on full-coverage
accuracy; it is not a headline claim.

\section{Case Study: State Resolution on a Fleet Operations Agent}
\label{sec:casestudy-fleetops}

The barrier case shows the deterministic floor stopping an action outright.
This one shows the mechanism that distinguishes the current architecture: what
happens when the action is well-formed and the \emph{state it refers to} is
uncertain. Both calls below are structurally perfect. They are routed
differently, and neither routing depends on a model's confidence.

\paragraph{Setup.} A fleet-operations agent has six tools, of which
\texttt{get\_vehicle}, \texttt{get\_driver}, \texttt{get\_work\_order} and
\texttt{list\_depot\_vehicles} are declared \texttt{read} and
\texttt{assign\_driver} and \texttt{close\_work\_order} are declared
\texttt{write}. The effects come from the registry, not from the verb in the
name, a distinction that matters, because \texttt{assign} and
\texttt{close} were once absent from a mutating-verb list and thirty writes
were scored as reads. No bulk state export exists, so every argument value
verdict is \textsc{unknown}: the deployment has point lookups and nothing else.

\paragraph{Call A: a legitimate read.} The user asks for the status of vehicle
\texttt{V-0042}; the agent proposes \texttt{get\_vehicle(vehicle\_id="V-0042")}.
Every structural signal is satisfied. The value is grounded: \texttt{V-0042}
is named in the task text. But \texttt{vehicle\_id} steers where the read
lands, and nothing has confirmed it exists, so autonomy is unavailable:

\begin{center}
{\footnotesize
\begin{tabular}{@{}ll@{}}
\toprule
Step & Outcome \\
\midrule
Argument support & \textsc{unknown} (no coverage declaration) \\
Value grounding & grounded (named in the task) \\
Validation requirement & required (steers the read) \\
Resolver availability & \texttt{get\_vehicle} bound to the role \\
Verdict & \textsc{verify} + \texttt{ResolutionPlan} \\
\midrule
\multicolumn{2}{@{}l@{}}{\emph{validator consulted; entity confirmed present}} \\
\midrule
Re-entry & whole router, fresh observation \\
Final verdict & \textsc{accept} \\
\bottomrule
\end{tabular}}
\end{center}

The plan names one resolver and exactly one argument it may write. The
validator returns a verdict and hands control back; it never performs the
original call and cannot redirect it. Re-entry re-runs the \emph{whole} router,
so every guard applies again to the confirmed call rather than being patched
around. Had no validator been bound to \texttt{vehicle\_id}, the verdict would
be \textsc{abstain}, not \textsc{verify}: promising a verification that cannot
happen is worse than stopping.

\paragraph{Call B: the same confirmation, a different action.} The agent
proposes \texttt{assign\_driver(work\_order\_id="WO-00123",
\texttt{driver\_id}="D-0017")}. Both identifiers confirm against the system of
record exactly as \texttt{V-0042} did. The call is nonetheless held at
\textsc{verify}: the registry declares this tool a write, and the read/write
posture does not trade confirmed state for autonomy on a state change. No
confidence score moves it.

\paragraph{Call C: structurally perfect, wrong tool.} The user asks for a
vehicle status; the agent proposes \texttt{get\_work\_order} with a work-order
identifier that happens to appear elsewhere in the task. Schema valid,
arguments satisfiable, values grounded, nothing tainted: every signal in
Call A's ladder is satisfied. The superseded C-ext2 track measured
wrong-call acceptance at 10.9\% without contracts (CLAIM-018). A declared
tool contract does: the task targets a vehicle, the tool acts on a work order,
and the mismatch is established rather than merely unverified. The sealed
C-ext3 track measured that authority with the frozen contract bundle and the
semantic-authority floor: native wrong-call acceptance fell to 0/500
(\S\ref{sec:wrongcall-implication}). That measurement does not cover Call C.
Only 2 of its 500 wrong calls name a tool the task itself offered
(NEGATIVE\_RESULTS.md \S83), so confusing two tools of one catalogue, as
here, is untested. The draft SAP v7 is to test it with wrong calls drawn
from the task's own catalogue and from model outputs.

\paragraph{Measured outcome.} The study behind the abstract's headline
is registered as CLAIM-014: under study conditions the validator loop
let 60/60 valid-identifier reads proceed autonomously in the
all-\textsc{unknown} regime, against 0/60 without validators, all eight pre-registered validator targets were met, and none
of 139 seeded corruption forms reached \textsc{accept} (artifacts:
\path{results/system_demonstration_v1.json},
\path{results/fleetops_degradation_results.json},
\path{results/fleetops_validator_study_results.json}; internal
benchmark, non-blind, the scope the register records).

\section{Negative Results}
\label{sec:negative}

The status of these findings, later mitigations and superseded results
is maintained in \texttt{NEGATIVE\_RESULTS.md}. The experiment-specific
constraints needed to interpret this paper's numbers remain beside
those results and in \S\ref{sec:threats}.

The complete protocol and outcome of the retired selection experiments
are preserved in \path{NEGATIVE_RESULTS.md} \S18 and claim register
CLAIM-012 / CLAIM-013. They are not current evidence for an execution
selector.

\paragraph{$\chi$-proxy failure.}
Susceptibility $\chi$ as standalone difficulty predictor: AUC = 0.39
on $N=302$ items, below chance. Exploratory OOD use (not a demonstrated
detector; the live variant is near-constant unless internal clamps bind):
$\chi > 1.45$ (97th percentile) $\Rightarrow$ \textsc{Escalate} with
\texttt{escalate\_adversarial}.

\paragraph{Critical-phase trust anticorrelation.}
Exploratory: the low/high split is 16/21 against 4/11, Fisher's exact
$p = 0.053$, and the augmented set uses simulated trust distributions.
Q4 high-trust: 50\% correct; Q1 low-trust: 75\% correct.
Confirmed on $N=32$ real-oracle items and replicated qualitatively
on augmented $N=511$ simulated dataset. No trust threshold separates
correct from incorrect critical-phase items (CLAIM-005). \emph{Consequence:}
evidence routing (not trust scoring) is the required mechanism for
critical-phase decisions.

\paragraph{The execution chain has only a post-hoc, author-run attack evaluation.}
Everything in \S\ref{sec:results} is measured on the research and
benchmark path. The authority-bound chain of \S\ref{sec:execution-chain}
(signed ToolSpec, exact-call lease, single-use grant, re-check at dispatch)
has unit, property and conformance tests. A post-hoc attack evaluation was
added after the review asked for one
(\path{scripts/execution_chain_attack_eval.py},
\path{artifacts/posthoc/execution_chain_attack_eval_v1.json},
NEGATIVE\_RESULTS.md \S87). It drives \texttt{/v1/execution} and a
policy-only gateway that takes the same proposal-time decision and then runs
whatever call is presented. The classes are replay, argument substitution,
ToolSpec redeploy or callable swap, risk relabel, cross-task, cross-actor
and cross-tenant reuse, forgery, expiry and approver role. REMORA ran 0 of
43 such attacks and the gateway ran 33. REMORA ran all 20 benign controls in
the catalogue.

Per-call authorization does not stop exfiltration through allowed calls.
The secret reached the sink in all 11 such attacks on both arms, either in a
read's URL or sent by a later allowed call. REMORA does not claim
trajectory-level or data-flow enforcement. The information-flow systems in
\S\ref{sec:related} \cite{wu2024fsecure,costa2025fides} target that case.
REMORA's own flow check is a library that no decision reads yet. The
catalogue is the author's own and is not an external benchmark. It runs in
one profile with in-process state and HMAC signing. Contribution~1 is
therefore a design and artifact contribution with a descriptive, author-run
attack measurement, not an independently measured security result.

\paragraph{Oracle diversity is partial.}
The retired Groq swarm used three LLaMA variants of one weight family, so
its consensus had an effective diversity closer to two. The 2026-07
cross-family trio (Meta LLaMA, Alibaba Qwen, Mistral) is enforced by a
fail-closed same-family check, but statistical independence is not
achievable with public models, and diversity weighting mitigates residual
correlation without removing it.

\paragraph{In-sample calibration.}
The selective threshold $\tau^* = 0.4991$ was chosen on a 436-item training
split and evaluated on the 108-item holdout of the same 544-item corpus, and
the signal and coverage target were chosen from an earlier run on that corpus
(\texttt{results/selective\_n500\_holdout\_results.json}); the SAP v1 round
locked $\tau^* = 0.203$ and is superseded; the decision envelope records this in
\texttt{in\_sample\_calibration\_warning}.

\paragraph{Evidence retrieval is proxy-based.}
The current \texttt{EvidenceSignal} is built from oracle consensus
statistics, not from passage retrieval or an NLI classifier over real
documents. The router is tested against MultiNLI as a proxy; real evidence
quality will differ.

\paragraph{Demo data.}
The Control Room frontend uses a seeded simulator for oracle votes,
latencies and evidence snippets, labelled as demo components; the backend
policy engine, observables and routing process real oracle responses.

\paragraph{MetaJudge circularity.}
AROMER's MetaJudge uses the same model family and provider as the
governance oracles, so biases common to that family go undetected. Its AII
component reflects within-family self-consistency more than external
validation.

\paragraph{Causal enrichment not deployed.}
The probability-of-sufficiency module is unit-tested, but live enrichment
of new episodes is not deployed, and no empirical results over real
governance episodes are reported for it.

\paragraph{No human evaluation of explanations.}
Trace faithfulness is machine-checked (the trace reproduces the engine's
decision rule for rule), but no user or expert study of comprehensibility
or actionability has been run. The paper claims traceability, not
explainability in the human-factors sense.

\paragraph{Boundary claims are declared, not closed.}
Three properties that bound every custody and dispatch claim in this
paper are explicitly unestablished
(\S\ref{sec:boundary-declarations}). Runtime capability-surface
completeness is \texttt{NOT\_ESTABLISHED}: the strict-profile custody
and dispatch evidence covers REMORA's own governed surface, and does
not establish that an external agent process lacks alternate
credential, network or execution paths. Implementation effect
non-transitivity is \texttt{NOT\_ESTABLISHED}: authorizing a tool does
not authorize every privileged effect its implementation can reach, so
the lease binds the exact call, not the effect space. Authoritative
execution-context binding is \texttt{NOT\_ESTABLISHED}: the opt-in
path is tested inside REMORA, the authority of its deployment sources
is not. The external run
records for the E-ECB, E-FA and E-EE contracts come from an external second
implementation and are recorded as not independent. The two E7 records are
independent under the repository's recorded rule and establish fixture
premises only. No boundary-level claim result is established by any of
them. The paper's custody claims
(\S\ref{sec:execution-chain}), and its title, should be read within
these declared limits: REMORA establishes properties at a declared
boundary and does not claim that all agent effects are governed.

\section{Threats to Validity}
\label{sec:threats}

\textbf{Internal validity:} Earlier QA operating points were selected
on limited or reused data and are retained as historical evidence in
\path{NEGATIVE_RESULTS.md} \S18. The benchmark also contains 13.8\%
author-curated items (15.1\% including the adversarial-curated set);
the tool-call benchmark uses synthetic adversarial patterns. The BFCL
tracks are an adaptive sequence of looks at one finite pool (v3, C-ext2,
C-ext3, C-ext4). Each track was ID-disjoint from the spent ones, but the
bundles were developed between looks on the same tool catalogue, and the
C-ext4 targets were set with the bundle's development numbers in hand.

\textbf{External validity:} Model coverage is mixed across rounds: the
earlier QA and tool-call rounds used a Groq-hosted three-LLaMA swarm
(one weight family, partial diversity), while the 2026-07 clean round,
the AgentHarm external validation, and the real-LLM baselines use a
Cloudflare Workers AI cross-family trio (Meta LLaMA, Alibaba Qwen,
Mistral). Results on other providers, closed-source models, or quantized
variants may still differ; the benchmark phase distribution may not match
deployment reality; and MultiNLI is a proxy for field evidence retrieval.

\textbf{Construct validity:} ``Trust'' is a derived scalar, not a frequency probability
of per-item correctness. Utility scores are designed task weights, not
real-world costs. The BFCL tracks route annotated gold proposals, and their
wrong calls are cross-task substitutions, not model errors
(\S\ref{sec:routing-blind}). Gold-call acceptance is a friction measure on
correct proposals, not task success, and is not comparable with BFCL
leaderboard scores. No external baseline (an LLM judge, an existing
guardrail) was run on the sealed BFCL episodes. Naive name-overlap and
schema-only rules were scored after the fact (NEGATIVE\_RESULTS.md \S83);
every other comparison is between REMORA configurations and a refuse-all
control. The
AII composite uses heuristic weights; AROMER reached TRAINED (AII 0.8442)
and regressed to CAPABLE (0.7885) the same day (CLAIM-006).

\textbf{Statistical validity:} 95\% Wilson confidence intervals are
reported for key accuracy figures. Formal hypothesis tests are not performed
across all conditions; where none is reported, overlapping or
non-overlapping intervals are not evidence of a difference. Zero-count
Wilson bounds treat rows as independent. The BFCL wrong calls share
proposed tools and REMORA's decision depends on the tool, and the AgentHarm
and tool-call scenarios share base behaviours and templates, so bounds
clustered at those levels are wider. Post hoc, the zero-count upper
bounds are 3.5\% over C-ext3's 106 tools, 5.42\% over C-ext4's 67 tools,
6.42\% over CLAIM-001's 56 harmful templates and 7.56\% over CLAIM-002's 47
base behaviours (NEGATIVE\_RESULTS.md \S83). The
tool-call benchmark's utility gain ($+0.46$ against the keyword
heuristics, $+0.26$ against the retired temperature-gate heuristic) is
a post-hoc test, declared
after the pre-registered hypothesis failed. Wilson intervals are fixed-$N$
constructions and are not valid under the continuous monitoring that the
REM-020 longitudinal gate performs (optional stopping). A time-uniform
confidence sequence
\cite{ville1939etude,darling1967confidence,howard2021timeuniform,ramdas2023game}
is therefore reported alongside for the gate's cycle-level false-accept
indicator: $0/168$ cycles gives a 95\% time-uniform upper bound of
4.72\% (\path{results/far_confidence_sequence_v1.json}, claim register
CLAIM-011). The sequence is wider than Wilson at any fixed $N$: the
price of validity under data-dependent stopping.

\section{Safety, Ethics, and Governance}
\label{sec:safety}

REMORA is designed to \emph{reduce} unsafe autonomous AI actions.
\textsc{Accept} means assurance conditions are met, not that the action
is correct. Human reviewers receiving \textsc{Escalate} retain full
accountability for outcomes. The oracle swarm routes sensitive
operational data through external APIs; data classification requirements
must be evaluated before deployment. The adversarial firewall detects
known injection patterns but is not a complete defense against
sophisticated adversarial inputs.

\paragraph{Fixture self-service vs.\ runtime reproduction.}

\section{Conclusion}
\label{sec:conclusion}

REMORA makes permission to execute a concrete agent action an explicit,
recorded decision. Its execution path binds that decision to a signed
tool definition, a single call and a single-use grant, then records
dispatch and observed effect as different claims. The studies reported
here examine three consequences of that design.

\textbf{The zero-unsafe result has no identified cause.} The
0\% unsafe-acceptance result on the adversarial tool-call benchmark (700
synthetic rows; 0 of 56 harmful templates, Wilson 95\% upper bound 6.4\%
over those templates; baselines 1.4\%, difference not significant at
$p=0.50$; a post-hoc test finds gains in utility, $+0.456$ against the
keyword heuristics and $+0.259$ against the temperature-gate heuristic,
and in accuracy) was observed with the deterministic policy gates in place, and
not produced by the multi-oracle consensus machinery. No experiment
attributes it to the gates: the committed component ablation records FAR
$=0.000$ in every condition,
including the one with the hard blocks removed, and so identifies no
component as necessary for the safety number (CLAIM-020). We state this against our
own interest: the probabilistic architecture that gives the system its
name is not what produces its headline safety number, and the
deterministic floor's share in it is unmeasured. Routing quality is a
different claim requiring different evidence.

\textbf{Unknown state is a resolution problem.} Absence without declared
completeness is \textsc{unknown}, not \textsc{unsupported}; a
\textsc{verify} that cannot name a bounded lookup degrades to
\textsc{abstain}; and a resolved value re-enters the whole router rather
than patching the prior decision. Under study conditions this lets 60/60
valid-identifier reads proceed autonomously in the all-\textsc{unknown}
regime, where none did without validators, with
zero corrupt-identifier acceptances, zero cross-tenant lookups, and
writes held at \textsc{verify} throughout.

\textbf{Routing holds within one tool catalogue.} The sealed C-ext3 track
isolated the semantic axis within one set of episodes: with declared tool
contracts and the semantic-authority floor, arm F accepted 0/500
substituted wrong calls (Wilson 95\% upper bound 0.76\% by row, 3.5\%
clustered by tool), against 24/500 for the structural arm (exact McNemar
$p = 1.2\times10^{-7}$, run after the fact). The same run missed four of
its seven pre-registered targets. Constructed wrong-tool acceptance was
2/199 against a safety bar of at most 1\%, read autonomy was 26.6\%
against 75\%, and both argument-routing targets were missed, so its
pre-registered joint hypothesis was not supported. The earlier C-ext2
track (CLAIM-018, superseded by CLAIM-019) met its five targets with
10.9\% (28/258) wrong-call acceptance on a different sample without
contracts; it stays on record as superseded and is not the comparison for
C-ext3. A third sealed track, C-ext4, raised
correct-call acceptance from 6.9\% to 29.9\% with every safety count at
zero, as for a refuse-all control; the gain sits mostly on tools seen in development, so generalisation
to unseen tool families is untested.

The current architecture offers two further research interfaces. Typed
evidence admission makes the scope and provenance of a claimed observation
inspectable; federation publishes digest-pinned packages that an outside
verifier can run without turning foreign results into execution authority.
The former is not yet wired into effect verification. External run
records now exist for the exact-call-binding, fresh-authority and
effect-evidence contracts (E-ECB, E-FA, E-EE), recorded as not independent.
The E7 runtime-surface contract has two external fixture-level runs that
meet the repository's independence rule, with every boundary-level claim
result still \texttt{NOT\_ESTABLISHED}. Contract
probes and a formal model from this repository found four findings in an
external federation transport, all fixed upstream
(\S\ref{sec:federation}). Experiment-specific constraints appear
beside the reported results and in \S\ref{sec:threats};
\texttt{NEGATIVE\_RESULTS.md} preserves the complete finding history.

What this paper does not show: transfer to a new tool catalogue,
discrimination against wrong calls that a model actually made, an advantage
over external or naive baselines, and the behaviour of the execution chain
under an external or adaptive attack (\S\ref{sec:negative},
\S\ref{sec:threats}).

REMORA remains \texttt{SHADOW\_ONLY}. It does not claim that all agent
effects are governed. It makes the governed boundary explicit, declares
what properties it can establish at that boundary, and publishes what it
cannot establish. Runtime capability-surface completeness and
implementation effect non-transitivity are among the published
non-claims. The bounded contracts it exposes can be reproduced by
outside operators. Production enforcement evidence and Federation
adoption remain unestablished. Its present contribution is a
reproducible account of where authority comes from, when a call may
proceed, and which evidence can support a claim about its effect.

\section{Retired Research Path: Consensus Observables}
\label{app:consensus}

This appendix and the two that follow hold the ensemble, conformal and
calibration material that the body summarises in
\S\ref{sec:method}, \S\ref{sec:evidence}, \S\ref{sec:results} and
\S\ref{sec:ablation}. None of it is on the governed execution path
(\S\ref{sec:observables-limits}), and no headline result depends on it.
It is kept because the numbers, the caveats and the negative results are
part of the record (\texttt{NEGATIVE\_RESULTS.md} \S18, \S38).

\subsection{Weighted Support Distribution}

Let $\hat{p}(v) = \sum_{o \in \OraclesV} w(o) \cdot
\mathbf{1}[\varphi(o)=v]$ be the diversity-weighted support for
verdict $v$, normalized to sum to 1. The diversity weight $w(o)$
penalizes oracles that frequently agree with others:
%
\begin{equation}
  w(o) = \frac{(1/n)}{1 + \sum_{j \neq o} \rho(o,j)} \cdot Z^{-1}
\end{equation}
%
where $\rho(o,j)$ is the rolling pairwise agreement rate (window 200
samples) and $Z$ normalizes. Oracles that agree with the swarm receive
lower weight; independent dissenters receive higher weight.
The rolling window persists for a long-lived engine instance (as in the
offline experiments); the reference API constructs a fresh engine per
request, so cross-request persistence of correlation state is a
deployment integration point, not a current runtime property.

\subsection{Core Observables}

\textbf{Shannon entropy} (computed over the token-fingerprint proxy
clustering in all reported experiments, not NLI-based semantic
clusters; backend note in \S\ref{sec:architecture}, limitations in
\S\ref{sec:threats}):
\begin{equation}
  H = -\sum_v \hat{p}(v) \log_2 \hat{p}(v) \quad \text{(bits)}
\end{equation}

\textbf{Dissensus:}
\begin{equation}
  D = 1 - \max_v \hat{p}(v)
\end{equation}

\textbf{Consensus concentration:}
\begin{equation}
  \eta = \frac{\max_v \hat{p}(v) - 1/k}{1 - 1/k}
\end{equation}
where $k = |\{v : \hat{p}(v) > 0\}|$ is the number of active verdicts.

\textbf{Trust score:}
\begin{equation}
  \trust = \eta \cdot (1 - h_{\text{bound}})
           \cdot w_{\text{phase}}
           \cdot \left(1 + \frac{\chi}{\chi_0}\right)^{-1}
\end{equation}
Here $h_{\text{bound}}$ is a heuristic risk proxy, not a proven bound;
$w_{\text{phase}}$ weights consensus regimes. This score describes
research routing, not an execution authorization. Implementation details
and the retired selection hypothesis are recorded in
\texttt{NEGATIVE\_RESULTS.md} (\S18, \S38).

\subsection{Oracle Count and Correlation Weighting}
\label{app:oraclecount}

\textbf{Oracle count ($N=302$).}
Single oracle: 56.95\% (95\% CI [51.3, 62.4]); three-oracle majority
vote: 82.78\% ([78.1, 86.6]), a gain of 25.8 pp; correlation-aware
weighting: 69.54\% ([64.1, 74.5]), below raw majority vote on
full-coverage accuracy. This is an exploratory ablation, not a headline
claim (\path{results/ablation_v2_results.json}). The value of correlation weighting
lies in trust calibration and selective coverage, not full-coverage
accuracy, and the primary benefit of the oracle swarm is disagreement
\emph{detection} (high $H$, high $D$).

Without correlation weighting, consensus from a within-family oracle
cluster would receive inflated support. The effect of the diversity
weights on trust scores and escalation rates has not been tested in a
controlled study that varies oracle family composition.

\section{Offline Critical-Phase Selection Components}
\label{app:selection}

The critical-phase trust inversion that motivates these components is
stated in \S\ref{sec:evidence}.

\subsection{PhaseAwareGuardrail: Exploiting Trust Inversion}
\label{sec:phase_aware}

The inversion is a \emph{selection criterion reversal}, not an
accuracy problem.  Items with $\tau < 0.10$ in the critical phase
achieve 76.2\% accuracy ($N=21$) vs.\ 36.4\% for high-$\tau$
critical items ($N=11$).  A \texttt{PhaseAwareGuardrail} exploits
this by applying an inverted score $\tilde{\tau} = 1 - \tau$ for
critical-phase items, then calibrating a conformal threshold on
$\tilde{\tau}$.  A hard gate rejects all items with $\tau \geq
\tau_{\max} = 0.10$ (the groupthink boundary) regardless of the
conformal result.

The combined pool, all 99 ordered-phase items (sorted by
$\tau \downarrow$) plus 21 low-$\tau$ critical items ($\tau < 0.10$,
sorted by $\tilde{\tau} \downarrow$), achieves:

\begin{itemize}[leftmargin=*]
  \item 20.0\% coverage ($N=108$): 85.2\% accuracy \text{CI~[77.3\%, 90.7\%]}
  \item 22.1\% coverage ($N=120$): 85.0\% accuracy \text{CI~[77.5\%, 90.3\%]}
\end{itemize}

This is a $+3.9$\,pp coverage gain over the ordered-only operating
point (18.2\%, 86.9\% accuracy), with a 1.9\,pp accuracy cost, still
$+43.8$\,pp above the 41.18\% full-coverage baseline.  The guardrail is
implemented in \path{remora.selective.guardrail.PhaseAwareGuardrail}
and fully tested (25 unit tests).

\subsection{PVD-Inspired Offline Agreement Score for Critical-Phase Routing}
\label{sec:pvd}

Kirchner et al.\ (2024) trained prover-verifier games that produce more
legible and reliable LLM outputs: helpful and sneaky \emph{provers}
justify claims to iteratively retrained small \emph{verifiers}
\cite{kirsch2024prover}. REMORA does \textbf{not} implement that training
game. The component below is a PVD-\emph{inspired}, post-hoc agreement
score computed over already-produced oracle responses: it selects two
existing responses, scores their agreement with the configured entailment
backend (default: token-fingerprint equality, not NLI), and applies a
fixed round decay. No model training, live interaction, argument
generation, or verifier update occurs, and it is not invoked by the
reference API (offline research component).

\paragraph{Protocol.}
\begin{enumerate}[leftmargin=*,label=\arabic*.]
  \item \textbf{Cluster} oracle responses via Semantic Entropy clustering
        \cite{kuhn2023semantic,farquhar2024detecting}
        (Appendix~\ref{app:consensus}), producing semantic equivalence classes
        $\mathcal{C} = \{C_1, \ldots, C_K\}$ sorted by mass.
  \item \textbf{Prover} = the oracle whose response belongs to the
        dominant cluster $C_1$ and has the highest per-oracle confidence.
  \item \textbf{Verifier} = the oracle with the highest confidence
        \emph{outside} $C_1$ (the independent challenger).
  \item \textbf{Deliberation} ($r = 1, \ldots, n_{\text{rounds}}$):
        evaluate bidirectional NLI entailment
        $e_r = \text{NLI}(\text{prover} \to \text{verifier}) \cdot \gamma^{r-1}$
        with round-decay factor $\gamma = 0.85$.
  \item \textbf{Legibility score}:
        $\mathcal{L} = \bar{e} \cdot |C_1| / N$,
        where $\bar{e}$ is the mean entailment and $|C_1|/N$ is the
        dominant cluster mass.
  \item \textbf{Final confidence}:
        $\hat{c} = \sqrt{|C_1|/N \cdot c_{\text{verifier}}}$
        (geometric mean of prover support and updated verifier confidence).
\end{enumerate}

\paragraph{Routing signal.}
The PVD confidence is blended with the raw REMORA trust score:
\begin{equation}
  \tilde{\tau} = (1 - w_{\text{pvd}}) \cdot \tau + w_{\text{pvd}} \cdot \hat{c},
  \qquad w_{\text{pvd}} = 0.40
  \label{eq:pvd_blend}
\end{equation}
In offline experiments this score can promote borderline critical-phase
items to \textsc{Accept} when agreement confidence is high, extending
coverage beyond the \texttt{PhaseAwareGuardrail} operating point. Neither
component is invoked by the reference API, and no formal risk bound
applies to this heuristic blend (Appendix~\ref{app:crc}).

\paragraph{Implementation.}
The deliberation entry point is
\begin{lstlisting}
remora.selective.pvd.deliberate(
    oracle_responses, oracle_confidences,
    n_rounds=2)
\end{lstlisting}
It returns a \texttt{PVDResult} with fields
\path{prover_cluster_mass}, \path{legibility_score},
\path{agreement}, and \path{final_confidence}.
\texttt{pvd\_routing\_score(trust\_score, pvd\_result)} implements
Eq.~\ref{eq:pvd_blend}.  Fully tested (33 unit tests, no external
model calls).

\section{Conformal Risk Control Under Covariate Shift (offline component)}
\label{app:crc}


Standard Mondrian conformal calibration assumes that calibration and
test samples are \emph{exchangeable} - drawn i.i.d.\ from the same
distribution.  This assumption is violated in the critical phase: the
joint distribution $(\tau, \text{correct})$ differs structurally
between ordered-phase calibration items and critical-phase test items
due to the trust-score inversion documented above.  Empirically,
applying standard conformal to critical-phase items yields 100\%
observed risk and zero coverage.

REMORA addresses this with a \textbf{weighted empirical selective
router} \emph{inspired by} Conformal Risk Control (CRC,
\cite{angelopoulos2022crc}) but, importantly, \emph{not
implementing the CRC procedure} (see below).  Each calibration item $i$
receives an importance weight $w_i = p_{\text{test}}(x_i) /
p_{\text{cal}}(x_i)$.  For REMORA's phase shift, we use the
hand-tuned estimate

\begin{equation}
  w_i = \begin{cases} 1.0 & \text{if phase}(i) = p_{\text{test}} \\
                      \beta & \text{otherwise} \end{cases}
  \qquad (\beta = 0.10)
  \label{eq:phase_weights}
\end{equation}

The selector picks the \emph{smallest} threshold $\hat{\lambda}$ (i.e.\
maximum coverage) such that the weighted empirical risk
$\bar{L}(\lambda) = \sum_i \tilde{w}_i \ell_i(\lambda) \leq \alpha$,
with $\tilde{w}_i = w_i / \sum_j w_j$ normalised over the calibration
items.

\begin{theorem}[CRC Guarantee, Angelopoulos et al.\ 2022, stated for
context; not instantiated by the implementation]
For any monotone loss $\ell : [0,1] \to [0,B]$, target risk
$\alpha \in (0,B)$, and correctly-specified importance weights:
\[
  \mathbb{E}[L(\hat{\lambda})] \leq \alpha + \frac{B}{n+1}
\]
where $n$ is the calibration set size.
\end{theorem}

\textbf{Non-applicability.} The implemented selector does not
instantiate this theorem, for two structural reasons no weight
specification can repair (external review R3-01): (a)~its threshold
rule applies the raw constraint $\bar{L}(\lambda) \leq \alpha$ with no
$B/(n+1)$ finite-sample term and no test-point weight $w_{n+1}$;
(b)~the controlled quantity, the conditional error rate among
accepted items, is not monotone in $\lambda$, so Theorem~1 does not
attach even with valid density-ratio weights. In addition,
$\beta = 0.10$ is a hand-tuned constant, not a density ratio
\cite{tibshirani2019conformal}. All quality evidence for this component is
empirical (repeated-split holdout results).

The component is implemented as
\path{remora.selective.crc.WeightedEmpiricalSelectiveRouter}
(formerly \texttt{CovariateShiftCRC}, retained as an alias) with a
\texttt{fit(scores, labels, phases, target\_phase)} interface
compatible with \texttt{ConformalPhaseGuardrail}.  A \texttt{CRCReport}
dataclass exposes \texttt{finite\_sample\_slack} ($= 1/(n_{\text{cal}}+1)$)
and \texttt{nominal\_risk\_bound} ($= \alpha + \text{slack}$) as
informational reference values (not applicable bounds), plus
\texttt{holdout\_risk} (plain unweighted holdout count). The module is
fully tested (45 unit tests) and is an
offline research component, not invoked by the reference API.

\section{Optional TEE-Based Audit Hardening (Tamper-Resistant)}
\label{app:tee}

\emph{This appendix describes tamper-resistant (not tamper-proof) audit hardening
via hardware attestation \cite{dong2025tee}. Implementation status: protocol specified; hardware
integration pending. The term ``tamper-resistant'' is used throughout; the
hash-chain in the main system is tamper-detecting only.}

\subsection{Motivation}

The SHA-256 hash-chain in \path{remora/audit/hash_chain.py} detects
post-hoc modification of audit records but does not prevent an adversary with
storage write access from replacing the entire chain. For deployments where
stronger guarantees are required, hardware attestation via a Trusted Execution
Environment (TEE) provides a complementary layer: the \texttt{DecisionEnvelope}
is signed inside a hardware-isolated enclave by a workload whose measurement
matches the approved build and policy digest, so silent substitution is
detectable even if storage is compromised. Attestation establishes which
code and configuration were measured; it does not establish that the model
or the policy decided correctly.

This is an optional deployment hardening; it is not required for the core
REMORA governance protocol described in the main paper.

\subsection{Supported TEE Platforms}

Three platforms are in scope for the reference implementation:
\begin{itemize}
  \item \textbf{Intel TDX / SGX} - remote attestation via DCAP quote generation
  \item \textbf{AMD SEV-SNP} - firmware measurement in attestation report
  \item \textbf{ARM TrustZone} - OP-TEE trusted application (mobile / edge)
\end{itemize}

\subsection{DecisionEnvelope Attestation Format}

When TEE hardening is active, each \texttt{DecisionEnvelope} includes an
\texttt{attestation} sub-object:

\begin{lstlisting}
{
  "envelope_id": "env_7f3a...",
  "gate": { "outcome": "ESCALATE", ... },
  "attestation": {
    "tee_platform": "intel_tdx",
    "quote":        "<base64 DCAP quote>",
    "mrenclave":    "<SHA-256 of enclave measurement>",
    "signature":    "<Ed25519 over envelope_id
                     +outcome+timestamp>",
    "timestamp":    "2026-01-15T14:23:07Z"
  }
}
\end{lstlisting}

The \texttt{mrenclave} value pins the exact binary that produced the decision,
allowing auditors to verify that no unauthorised code modification occurred
between decisions.

\subsection{Verification Flow}

\begin{enumerate}
  \item Auditor retrieves envelope and attestation quote from audit log.
  \item Quote is verified against Intel/AMD/ARM attestation service.
  \item \texttt{mrenclave} is compared against the published release measurement.
  \item Ed25519 signature over \texttt{(envelope\_id, outcome, timestamp)} is
        verified with the enclave's ephemeral key, which is bound to the quote.
\end{enumerate}

If any step fails, the audit record is flagged as potentially tampered.

\subsection{Implementation Status}

Protocol specified and data contract defined. Hardware integration (enclave
compilation, DCAP provisioning, OP-TEE TA signing) is a deployment
dependency and is not part of the core source-available release. Stub interfaces
are present in \texttt{remora/audit/} for downstream integration.
